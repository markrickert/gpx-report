## Planned features

- [ ] **Chair lift / uplift detection, general-purpose across activity types.** Not limited to skiing/downhill MTB — hiking routes can include chairlift/gondola segments too (e.g. hike up, ride a lift down, or vice versa), so this should be a general track-analysis tool run against any activity's points, not gated by `activityType`. Detect stretches of the track that are a lift ride (rather than the athlete's own effort) and render that range with a distinct background band on the elevation graph (`ActivityDetail.jsx`'s recharts chart, same `ReferenceArea` mechanism already used for the trim range). Uplift-gained elevation should then be excluded from `total_elevation_gain` (a chairlift ride isn't "climbing"), which needs either a new stored field (e.g. `lift_elevation_gain`) or computing it live from `points_data`/`elevation_profile_data` — worth deciding whether to persist per-activity or derive at query time. A fun derived stat: total elevation gained vs. elevation gained minus lift segments (illustrates how much of a ski day's "gain" was actually earned). Detection heuristic per the user: chairlifts run in a straight line, at roughly constant speed, with occasional stops under a few minutes each, and almost always constant/steady altitude gain (no noisy up-down like self-powered movement) — distinct from a hiker's or skinner's noisier stop-start pace and irregular elevation profile. Since the heuristic is track-shape-based rather than activity-type-based, it should naturally leave paragliding tracks alone (thermalling doesn't look like a straight-line constant-speed lift ride) without needing an explicit type exclusion — same class of tuning decision as the existing GPS-outlier and lead-in/trailing-inactivity ideas above.

- [ ] **Auto-suggested crop for lead-in/trailing inactivity.** The trim editor on `ActivityDetail.jsx` requires manually dragging the handles; detect long stretches of near-zero movement (GPS jitter aside) at the start/end of a track's points and pre-position the trim handles at the suggested crop range instead of the full track, still leaving the user free to adjust before saving. Needs a stillness threshold/window decision (same class of tuning as the GPS-outlier-detection idea above) — e.g. flag a leading/trailing run where point-to-point speed stays under some cm/s for some minimum duration.
- [ ] **Nicer-looking, smarter-default Heatmap page.** Visual pass on `/heatmap` (currently a plain `leaflet.heat` layer over the basemap) plus a smarter initial view: default the map's center/zoom to the bounding box of recent high-density activity (e.g. last N months' most-active area) instead of a fixed world/region view, so it opens already zoomed into where the user has actually been active lately.
- [ ] **Graceful degradation without JavaScript.** The frontend is a pure client-rendered Vite/React SPA with an empty `<div id="root">` — JS disabled currently means a blank page. Fixing this for real needs SSR/static pre-rendering, a genuine architecture shift, not a small tweak. Scope (which routes, read-only vs. the editing/trim features that need client interactivity anyway) still needs a decision before committing to a framework.
- [ ] **Delete/archive an activity.** No delete path exists anywhere — no mutation, no resolver, no UI. Needs a decision on whether it also deletes/moves the source file (so the watcher/re-analysis don't just re-ingest it) or only hides the DB row.
- [ ] **Heart rate / cadence / power support.** `gpx/parser.js` only reads lat/lon/elevation/timestamp — it ignores Garmin's `gpxtpx:TrackPointExtension` (`hr`, `cad`, `atemp`) even when present in the source file. Would need new `points_data` fields, new `activities` summary columns (avg/max HR), and a chart on `ActivityDetail.jsx`. IGC/`.skiz` don't carry this data at all, so it'd be GPX-only.
- [ ] **"You've done this route before" / similar-route detection.** `activity_routes.route_geom` is PostGIS-typed and GiST-indexed but no resolver ever queries it spatially (confirmed: no `ST_DWithin`/`ST_Distance` anywhere in `resolvers.js`). Could power a "similar past activities" section on `ActivityDetail.jsx` using `ST_DWithin`/`ST_HausdorffDistance` — the stored geometry already supports it, this is resolver + UI work only, no schema change.
- [ ] **Personal records / best-effort segments.** Fastest 1km/5km/10km, longest distance, biggest elevation gain, etc., per `activityType`, surfaced on the Stats page and/or as a badge on `ActivityDetail.jsx` when an activity sets a new one. Computable from `points_data`/`elevation_profile_data` already stored — no new ingestion needed, but the fastest-segment calc itself (sliding window over trackpoints) is nontrivial and should be scoped before starting.
- [ ] **Activity notes/description field.** A freeform text field per activity (route conditions, how it felt, gear used) — unlike title/type, doesn't need to round-trip into the source GPX file, so it can be a plain new `activities` column with no writer.js changes.
- [ ] **Full data export/backup.** A way to download a zip of all source files + a DB dump (or a JSON export of all `activities`/`activity_routes` rows), distinct from the per-activity download above — for off-site backup or migrating to a different host. `data/gpx/` and the Postgres volume are the only copies of this data today.
- [ ] **Search activities by title.** The Dashboard filters by `activityType` only; there's no text search over `title`, which becomes more useful as the multi-hundred-activity ingestion history (91 `.skiz` files alone) grows.
- [ ] **Compare two activities side-by-side.** Pick a second activity from `ActivityDetail.jsx` (e.g. same trail, different day) and overlay their elevation profiles / show a stats diff table. No backend change needed — `activity(id)` already returns everything required, this is a frontend view.
- [ ] **Training volume trend chart.** Bar/line chart of distance or duration per week/month over time, filterable by `activityType` — a Stats-page companion to the existing calendar heatmap, answering "am I doing more or less than last month" rather than "which days." Computable from the existing lightweight `activities(limit: 1000)` fetch already used by the heatmap.
- [ ] **Speed/pace-colored route on the map.** Instead of a flat-color polyline, render the route as segments colored by point-to-point speed (already computed into `elevationProfile`'s `speedMps`), so slow/fast sections are visible at a glance on `ActivityDetail.jsx`'s map.
- [ ] **Reverse-geocoded location name per activity.** Resolve the start point's lat/lon to a place name (city/trailhead) via a geocoding API and show it on the Dashboard list / Activity Detail header instead of just date+type. Needs picking an external geocoding service (rate limits, possibly a paid key) — worth a decision before starting, unlike the DB-only ideas above.
- [ ] **Elevation profile smoothing.** Raw GPS elevation is noisy (barometric/GPS jitter shows as sawtooth gain/loss); a smoothing pass (e.g. rolling average or Douglas-Peucker-style simplification) before computing `total_elevation_gain/loss` would make those numbers and the chart more trustworthy. Would need before/after validation against a few known routes to avoid quietly changing everyone's historical stats.
- [ ] **Bulk actions on the Dashboard.** Multi-select activities to retype or delete in one operation (depends on the delete mutation above existing first), instead of the current one-at-a-time inline editing on each Activity Detail page.
- [ ] **CSV export of the activity list / stats table.** A "download as CSV" on the Dashboard list or the Stats per-type table, for opening in a spreadsheet — simpler and narrower than the full zip/DB-dump backup idea above.
- [ ] **Push/toast notification when a new activity finishes ingesting.** Currently the only feedback that a synced file was processed is seeing it appear in the Dashboard list. Since PWA installability already exists, a Notifications API toast ("Morning Run ingested") when the watcher completes a file would close that loop — foreground-only unless paired with a service-worker push, which needs a server-side trigger this app doesn't have yet.
- [ ] **Moving time vs. total time.** `avg_speed_mps` is currently `distance / (end_time - start_time)`, which includes stopped time (traffic lights, breaks, photo stops) and understates real pace. Detecting "stopped" via a speed threshold on consecutive points and computing a separate moving-time average would be more honest — needs a decision on the stillness threshold and whether to keep both numbers or replace the existing one.
- [ ] **Streak / consistency tracker.** Current consecutive-day (or consecutive-week) streak of at-least-one-activity, plus longest streak ever — a small derived stat, computable from `start_time` alone, no new ingestion.
- [ ] **Rolling training load (acute:chronic workload ratio).** 7-day vs. 28-day rolling distance or duration totals, the "am I ramping up too fast" signal runners/cyclists use to gauge injury risk — pure derived stat off existing `distance_meters`/`start_time`, no HR needed (unlike the fuller HR-based training-load idea above).
- [ ] **Grade-adjusted pace.** On hilly routes, raw pace makes climbs look "slow" and descents look "fast" even at equal effort. A grade-adjustment formula against the existing per-point elevation/distance data would give a fairer effort-normalized pace, useful once the personal-records feature above exists (so a hilly PR isn't unfairly compared to a flat one).
- [ ] **GPS outlier / teleport detection.** A single bad GPS fix (device jumps 500m in one second) can silently inflate `distance_meters`/`max_speed_mps`. A sanity filter (reject implausible point-to-point speed jumps before computing stats) in the parsers would catch this — worth auditing a few existing activities for suspiciously high max speeds first to see if it's a real problem before building it.
- [ ] **This-year-vs-last-year comparison.** Same date-range-to-date totals (distance, count, elevation) for the current year vs. the prior year, on the Dashboard or Stats page — motivating without being social, since it's purely self-referential.
- [ ] **"On this day" recap.** Surface past activities that happened on today's date in prior years, e.g. a small Dashboard card — cheap query (`WHERE EXTRACT(MONTH/DAY FROM start_time) = ...`), no new schema.
- [ ] **Ad-hoc stat correlation / scatterplot builder.** A Stats-page tool to plot any two numeric fields against each other (distance vs. elevation gain, time-of-day vs. pace, day-of-week vs. distance) instead of only the fixed heatmap/breakdown views — for spotting personal patterns the built-in views don't surface.
- [ ] **Raw data export for external analysis.** A "download everything as JSON/CSV" built for feeding into Python/Jupyter/a spreadsheet for analysis this app doesn't do itself — overlaps with the full-backup idea above but framed around analysis portability rather than disaster recovery, so worth keeping distinct in scope discussions.

## Known gaps

- [ ] **No DB migration tooling.** `backend/db/init.sql` only runs against a fresh volume. Any schema change to an already-deployed instance needs a manual `psql`/`ALTER` step. Fine for now (single-user, low change rate) but worth a lightweight migration runner if schema churn picks up.
- [ ] **No typecheck config anywhere in the repo.** ESLint/Prettier and backend parser unit tests now exist (see Done above); typechecking is still unaddressed, and frontend/GraphQL-layer test coverage remains thin.
- [ ] **No auth on the API or frontend.** Acceptable for now since the intended deployment is Caddy + Tailscale (see `docs/SETUP.md` §6 reverse-proxy notes), but if the API/frontend domains are ever exposed outside Tailscale, this becomes a real gap, not just a v1 simplification.

## Explicitly out of scope for v1 (not gaps, just noting so they don't get re-litigated)

- No in-app GPX upload/file management — files are expected to arrive via Syncthing or manual drop into `data/gpx/`.
- No multi-user support.
