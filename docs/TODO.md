Stillness threshold: reuse whatever threshold the existing rest-stop-band detector on `ActivityDetail.jsx` already uses, rather than inventing a new one, for consistency.
- [ ] **Nicer-looking, smarter-default Heatmap page.** Visual pass on `/heatmap` (currently a plain `leaflet.heat` layer over the basemap) plus a smarter initial view: default the map's center/zoom to the bounding box of recent high-density activity (e.g. last N months' most-active area) instead of a fixed world/region view, so it opens already zoomed into where the user has actually been active lately.
- [ ] **Delete/archive an activity.** No delete path exists anywhere — no mutation, no resolver, no UI. Deletes the source file from `data/gpx/` as well as the DB row (not a DB-only hide), so the watcher/re-analysis don't re-ingest it on restart/rescan.
- [ ] **Heart rate / cadence / power support.** `gpx/parser.js` only reads lat/lon/elevation/timestamp — it ignores Garmin's `gpxtpx:TrackPointExtension` (`hr`, `cad`, `atemp`) even when present in the source file. Scope: full support from the start — new `points_data` fields, new `activities` summary columns (avg/max HR), and a synced chart on `ActivityDetail.jsx` alongside the elevation profile, not just summary numbers. IGC/`.skiz` don't carry this data at all, so it'd be GPX-only.
- [ ] **"You've done this route before" / similar-route detection.** `activity_routes.route_geom` is PostGIS-typed and GiST-indexed but no resolver ever queries it spatially (confirmed: no `ST_DWithin`/`ST_Distance` anywhere in `resolvers.js`). Could power a "similar past activities" section on `ActivityDetail.jsx` using `ST_DWithin`/`ST_HausdorffDistance` — the stored geometry already supports it, this is resolver + UI work only, no schema change.
- [ ] **Personal records / best-effort segments.** Fastest 1km/5km/10km, longest distance, biggest elevation gain, etc., per `activityType`, surfaced on the Stats page and/or as a badge on `ActivityDetail.jsx` when an activity sets a new one. Computable from `points_data`/`elevation_profile_data` already stored — no new ingestion needed, but the fastest-segment calc itself (sliding window over trackpoints) is nontrivial and should be scoped before starting.
- [ ] **Full data export/backup.** A way to download a zip of all source files + a DB dump (or a JSON export of all `activities`/`activity_routes` rows), distinct from the per-activity download above — for off-site backup or migrating to a different host. `data/gpx/` and the Postgres volume are the only copies of this data today.
- [ ] **Compare two activities side-by-side.** Pick a second activity from `ActivityDetail.jsx` (e.g. same trail, different day) and overlay their elevation profiles / show a stats diff table. No backend change needed — `activity(id)` already returns everything required, this is a frontend view.
- [ ] **Training volume trend chart.** Bar/line chart of distance or duration per week/month over time, filterable by `activityType` — a Stats-page companion to the existing calendar heatmap, answering "am I doing more or less than last month" rather than "which days." Computable from the existing lightweight `activities(limit: 1000)` fetch already used by the heatmap.
- [ ] **Speed/pace-colored route on the map.** Instead of a flat-color polyline, render the route as segments colored by point-to-point speed (already computed into `elevationProfile`'s `speedMps`), so slow/fast sections are visible at a glance on `ActivityDetail.jsx`'s map.
- [ ] **Reverse-geocoded location name per activity.** Resolve the start point's lat/lon to a place name (city/trailhead) via a geocoding API and show it on the Dashboard list / Activity Detail header instead of just date+type. Service: Nominatim (OSM, free, no key) — rate-limited to 1 req/s, fine for one-off per-activity lookups triggered on ingest, not for bulk backfill without throttling.
- [ ] **Elevation profile smoothing.** Raw GPS elevation is noisy (barometric/GPS jitter shows as sawtooth gain/loss); a rolling-average smoothing pass before computing `total_elevation_gain/loss` would make those numbers and the chart more trustworthy. Ship directly with a reasonable window, no formal before/after validation step — watch for complaints if historical stats shift noticeably.
- [ ] **Bulk actions on the Dashboard.** Multi-select activities to retype or delete in one operation (depends on the delete mutation above existing first), instead of the current one-at-a-time inline editing on each Activity Detail page.
- [ ] **Push/toast notification when a new activity finishes ingesting.** Currently the only feedback that a synced file was processed is seeing it appear in the Dashboard list. Since PWA installability already exists, a Notifications API toast ("Morning Run ingested") when the watcher completes a file would close that loop — foreground-only unless paired with a service-worker push, which needs a server-side trigger this app doesn't have yet.
- [ ] **Moving time vs. total time.** `avg_speed_mps` is currently `distance / (end_time - start_time)`, which includes stopped time (traffic lights, breaks, photo stops) and understates real pace. Detecting "stopped" via a speed threshold on consecutive points and computing a separate `moving_avg_speed_mps` (new column, added alongside — existing `avg_speed_mps` stays as-is, no historical stat silently changes) would be more honest.
- [ ] **Grade-adjusted pace.** On hilly routes, raw pace makes climbs look "slow" and descents look "fast" even at equal effort. A grade-adjustment formula against the existing per-point elevation/distance data would give a fairer effort-normalized pace — standalone stat/chart on `ActivityDetail.jsx`, no dependency on the personal-records feature existing first.
- [ ] **Ad-hoc stat correlation / scatterplot builder.** A Stats-page tool to plot any two numeric fields against each other (distance vs. elevation gain, time-of-day vs. pace, day-of-week vs. distance) instead of only the fixed heatmap/breakdown views — for spotting personal patterns the built-in views don't surface.
- [ ] **Two-finger rotate gesture on the activity map.** `ActivityDetail.jsx`'s map (Leaflet via `react-leaflet`) only pans/zooms on touch; stock Leaflet has no bearing/rotation concept at all, so this needs a rotation-capable plugin (e.g. `leaflet-rotate`) wired into the existing `MapContainer`, plus a way to reset bearing back to north (could fold into the existing reset-view button).
- [ ] **Raw data export for external analysis.** A "download everything as JSON/CSV" built for feeding into Python/Jupyter/a spreadsheet for analysis this app doesn't do itself — overlaps with the full-backup idea above but framed around analysis portability rather than disaster recovery, so worth keeping distinct in scope discussions.

- [x] **Rolling training load (acute:chronic workload ratio)** (2026-08-07) — new `trainingLoad` GraphQL query sums `distance_meters` over the last 7 days (acute) and last 28 days averaged to a weekly rate (chronic, `28-day sum / 4`) via `FILTER` clauses in one SQL statement, then divides acute by chronic-weekly-avg for the ratio (`null`, not NaN/Infinity, when chronic load is 0) with a qualitative label ("ramping up" above 1.5, "detraining" below 0.8, "steady" otherwise). Distance-based rather than duration-based, matching the app's existing km/mi-first convention. Rendered as three `summary-tile`s on the Stats page next to the streak/year-over-year tiles.
- [x] **This-year-vs-last-year comparison** (2026-08-07) — new `yearOverYearComparison` GraphQL query, a single SQL statement using `FILTER` clauses to sum `activities` in two ranges: `date_trunc('year', CURRENT_DATE)` through `CURRENT_DATE` for the current year, and the same range shifted back one year via `INTERVAL '1 year'` for the prior year — date-range-to-date (Jan 1 through today's month/day), not full-year totals, so an in-progress year isn't compared unfairly against a completed one. Rendered as a `summary-tile` row on the Stats page (same pattern as the streak tiles just above it) showing activity count/distance/elevation gain for each year plus a `+X%`/`-X%` delta, colored via new `--success`/`--danger` tile-delta classes.

## Known gaps

- [ ] **No DB migration tooling.** `backend/db/init.sql` only runs against a fresh volume. Any schema change to an already-deployed instance needs a manual `psql`/`ALTER` step. Fine for now (single-user, low change rate) but worth a lightweight migration runner if schema churn picks up.
- [ ] **No typecheck config anywhere in the repo.** ESLint/Prettier and backend parser unit tests now exist (see Done above); typechecking is still unaddressed, and frontend/GraphQL-layer test coverage remains thin.
- [ ] **No auth on the API or frontend.** Acceptable for now since the intended deployment is Caddy + Tailscale (see `docs/SETUP.md` §6 reverse-proxy notes), but if the API/frontend domains are ever exposed outside Tailscale, this becomes a real gap, not just a v1 simplification.
- [ ] **Node 18 is stale and breaks tooling.** Both the host/dev environment and the Docker base images are pinned to Node 18; Vitest's `rolldown` dependency needs `node:util`'s `styleText` export (Node ≥20), so `backend && npm test` currently fails to even start outside a Node 22 shell. Upgrade the Docker base images (`backend/Dockerfile`, `frontend/Dockerfile`) and any documented dev-environment Node version to a current LTS (22.x).

## Explicitly out of scope for v1 (not gaps, just noting so they don't get re-litigated)

- No in-app GPX upload/file management — files are expected to arrive via Syncthing or manual drop into `data/gpx/`.
- No multi-user support.
- No graceful degradation without JavaScript. The frontend is a pure client-rendered Vite/React SPA — JS disabled means a blank page. Fixing this needs SSR/static pre-rendering, a genuine architecture shift not warranted for a personal single-user tool.
