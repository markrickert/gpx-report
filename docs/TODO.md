## Done

- [x] **`aggregatedStatsByType` query wired up** (2026-08-06) — new `/stats` nav tab (`frontend/src/pages/Stats.jsx`) renders a table of per-activity-type totals/averages (count, total/avg distance, total/avg duration, avg elevation gain) via a new `GET_STATS_BY_TYPE` query (`frontend/src/graphql/queries.js`). Uses the shared unit toggle (`units.jsx`) for distance/elevation. No date-range filter UI yet — the query supports `startDate`/`endDate` but this view always calls it unfiltered (all-time breakdown); a "this year" style filter wasn't asked for.
- [x] **Editable activity type, from a preselected list** (2026-08-06) — `ActivityDetail.jsx` gets an Edit/Save/Cancel affordance next to the activity-type badge (mirrors the existing title-edit flow), backed by a dropdown of the same 10 types Dashboard's filter uses (now shared via `frontend/src/activityTypes.js` instead of being defined twice, plus an "Unknown" option so activities without a guessable type can be left as-is). New `updateActivityType(id, activityType)` mutation (`backend/src/graphql/{typeDefs,resolvers}.js`) writes the `<trk><type>` element via a new `updateGpxType()` in `backend/src/gpx/writer.js` (same string-replace approach as the title writer), then re-runs `processFile()`. Since `gpx/parser.js`'s `resolveActivityType()` reads `<type>` back through a raw-value-to-label table (e.g. `mountain_biking` → "Mountain Biking"), the mutation converts the selected label back to its raw key first via a new `activityTypeToRawType()` export, so the round-trip lands on the exact label chosen rather than parser.js's generic camelCase/snake_case formatter guessing a slightly different string.
- [x] **`.igc` file support (paragliding)** (2026-08-06) — new `backend/src/igc/parser.js` (`parseIgcFile`) parses IGC B-records (lat/lon/altitude/timestamp per fix) and `HFDTE` date headers via regex, computing distance/speed/elevation stats with a haversine helper (IGC has no precomputed distances the way `gpxparser` gives GPX), returning the same shape `gpx/parser.js`'s `parseGpxFile` does. `gpx/processor.js`'s `processFile()` now dispatches to whichever parser matches the file extension; `listGpxFiles`/the watcher (`gpx/watcher.js`) now match `.gpx` and `.igc`. IGC has no track-name/type header equivalent to GPX's `<trk><name>/<type>`, so title falls back to the filename stem and `activityType` is fixed to `"Paragliding"` (the only IGC source in use). Title/type editing (`updateActivityTitle`/`updateActivityType`) only works for `.gpx` files — `writer.js` only knows how to rewrite GPX XML — so both mutations now reject non-`.gpx` activities with a clear error, and `ActivityDetail.jsx` hides the Edit buttons for those activities (`gpxFilename` added to `GET_ACTIVITY`).

- [x] **Trim editing on the elevation profile** (2026-08-06) — no separate speed-vs-time chart added; the existing elevation `LineChart` on `ActivityDetail.jsx` already encodes speed (gradient line color) and rest stops (shaded bands), so trim editing landed on that one chart. Entering edit mode (existing Edit button, same `editMode` flag used by title/type editing) reveals two vertical drag handles directly on the chart (one per end of the kept range, rendered as a `ReferenceLine` + a circular `ReferenceDot` grab-knob per handle), draggable back and forth along the timeline via pointer/touch events routed through recharts' own `onMouseMove`/`onTouchMove` `activeTooltipIndex` (pixel-accurate against the chart's real scale, no manual pixel math). The chart shades whichever head/tail is currently cropped out via `ReferenceArea`, made more opaque than the kept region so it reads as "will be removed"; that shading (and the handles) stay until the trim is actually saved and the page's data is reloaded, at which point edit mode exits and the activity is back in plain data-viewing mode. The map polyline re-slices live as the handles move. New `trimActivity(id, startIndex, endIndex)` mutation (`backend/src/graphql/{typeDefs,resolvers}.js`) calls a new `trimGpxTrack()` in `backend/src/gpx/writer.js` (drops `<trkpt>` elements outside the kept index range via the same string-replace approach as the title/type writers, matching indices 1:1 against `parser.js`'s point order) then re-runs `processFile()`. Saving shows a `window.confirm` first, since it permanently deletes GPX track points with no undo; only `.gpx` activities get the trim UI, matching the existing title/type edit restriction.
  - **Recharts gotcha found and fixed while building this** (also silently affected the pre-existing rest-stop shading): the elevation chart's `XAxis` is keyed on `dist` (distance rounded to 2 decimals for display), which collides constantly on real tracks — a 240-point activity had only 154 unique `dist` values. Recharts' `ReferenceLine`/`ReferenceArea`/`ReferenceDot` silently render nothing at all (no error, no DOM node) when their `x`/`x1`/`x2` is matched against a category axis with duplicate values — confirmed via an isolated repro outside the app. Fix: added a second, hidden `XAxis` keyed on a synthetic always-unique `idx` field (`xAxisId="idx"`, `allowDuplicatedCategory={false}`) and pointed every `Reference*` component (rest-band shading included) at that axis via integer point indices instead of the `dist` string. Also: recharts only recognizes `Reference*` components as *direct* children of the chart — conditionally rendering a group of them wrapped in a `<>` Fragment silently drops all of them too, so each is its own top-level `{condition && (...)}` expression.

## Known gaps

- [ ] **No DB migration tooling.** `backend/db/init.sql` only runs against a fresh volume. Any schema change to an already-deployed instance needs a manual `psql`/`ALTER` step. Fine for now (single-user, low change rate) but worth a lightweight migration runner if schema churn picks up.
- [ ] **No automated tests, lint, or typecheck config anywhere in the repo.** Noted as current state in `CLAUDE.md`; flagging here as something to eventually add rather than silently keep deferring.
- [ ] **No auth on the API or frontend.** Acceptable for now since the intended deployment is Caddy + Tailscale (see `docs/SETUP.md` §6 reverse-proxy notes), but if the API/frontend domains are ever exposed outside Tailscale, this becomes a real gap, not just a v1 simplification.

## Explicitly out of scope for v1 (not gaps, just noting so they don't get re-litigated)

- No in-app GPX upload/file management — files are expected to arrive via Syncthing or manual drop into `data/gpx/`.
- No multi-user support.
