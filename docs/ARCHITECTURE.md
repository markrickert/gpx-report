# Architecture Overview

This document outlines the architecture of gpx-report, a self-hosted platform for analyzing GPX activity data.

## 1. Frontend (Universal Expo App)

*   **Purpose:** One codebase with two jobs: the web UI for viewing, analyzing, and managing activity data on a big screen, and the iOS/Android app for recording activities with background GPS.
*   **Technology:** Expo (SDK 57) + Expo Router, React 19, TypeScript (loose `tsconfig`, `strict: false`, matching the pre-Expo web code it carried over). The web build is a static SPA (`web.output: "single"`, template in `frontend/public/index.html`).
*   **Platform split:** Routes live in `frontend/src/app/`. A route with a `.web.tsx` sibling gets a different screen per platform — e.g. `(tabs)/(history)/index.tsx` is the phone's History list while `(tabs)/(history)/index.web.tsx` is the web people picker. The web-only analysis pages (`frontend/src/screens/web/`) are plain DOM + CSS (`src/web.css`) with `react-leaflet`/`recharts`, not React Native components; they link via `components/web-link.tsx`, a real `<a>` that calls `router.push`. Routes that only exist on web have a native fallback that redirects to History. The web root layout (`_layout.web.tsx`) is the nav shell; the native root layout is a Stack over NativeTabs (History / Record / Settings), and each tab is its own Stack (`components/tab-stack.tsx`) so it gets a title bar.
*   **Per-person web URLs:** every web analysis page lives under `src/app/[person]/` (`/<person>`, `/<person>/stats`, `/<person>/activities/:id`, …); `[person]/_layout.web.tsx` swaps in that person's Apollo client, and pages build links with `lib/person.ts`'s `usePersonHref()`. `/` is a people picker, `/code` stays global, and the pre-accounts URLs (`/stats`, `/heatmap`, `/settings`, `/record`, `/activities/:id`) redirect to the default person's (`/mark/...`) so old bookmarks keep working. The nav shell derives the current person from the route params.
*   **Key Components:**
    *   **Dashboard:** Displays aggregate statistics and a chronological list of activities, filterable by activity type.
    *   **Activity Detail Page:** Shows detailed metrics, map visualization, and elevation profile for a single activity.
    *   **Settings Page:** Triggers re-analysis (last week / month / year / all time), and lists activities flagged by the GPS outlier detector and the lift detector (both below) for manual review.
    *   **Record (phone only):** One React Native screen (`screens/record.tsx`). The web app has no recorder — a browser stops delivering GPS once the tab is backgrounded or the screen locks — so its `/record` route redirects to the dashboard. Location comes from `recording/location-source.ts` (`startLocationUpdatesAsync` + the TaskManager task in `recording/task.ts`, imported at module scope from the root layout so it's registered before the OS delivers background locations). Points go to `recording/store.ts` (expo-sqlite; `store.web.ts` is an in-memory stand-in used only by the Vitest suite), and the screen polls the store once a second rather than holding points in React state.
    *   **Upload queue (`recording/upload-queue.ts`):** builds the GPX (`recording/gpx.ts`) at upload time and sends it with the recording UUID as `clientId`. Failures back off exponentially; `hooks/use-upload-queue-triggers.ts` re-runs it on network change, foreground, and a timer.
*   **Data Interaction:** Communicates with the backend via a GraphQL API (`@apollo/client`).
*   **Mapping:** web: `react-leaflet` / `leaflet`; native: `expo-maps` — Apple Maps on iOS (no key), Google Maps on Android (API key from `GOOGLE_MAPS_API_KEY`, injected by `frontend/app.config.ts`). `expo-maps` is alpha in SDK 57, and neither view can fit bounds, so the native wrapper estimates a zoom from the track's extent. `components/live-track-map.tsx` / `.web.tsx` wrap each.
*   **Charting:** `recharts` for the elevation profile.
*   **Server URL:** `lib/apollo.ts` resolves the GraphQL URL per request: a user override from `localStorage` (polyfilled on native by `expo-sqlite/localStorage/install`) or `EXPO_PUBLIC_GRAPHQL_URL`, else `/graphql` on the web (same origin) and `http://localhost:4000/graphql` on native. The phone sets the override from Settings. Production web needs no URL: the frontend container's Caddy (`frontend/Caddyfile`) serves the bundle and proxies `/graphql` and `/api/*` to the backend, so the whole app is one origin.
*   **Person:** `lib/apollo.ts`'s `clientFor(person)` keeps one `ApolloClient` per person, each sending an `X-GPX-Person` header, so one person's cached lists never leak into another's view. The phone's person is the "Your name" set in Settings (`lib/person.ts`, `localStorage`); each recording captures it at Start (`recordings.person`) and the upload queue sends it through that person's client, so renaming later doesn't reassign an in-flight recording.
*   **Build tool:** Metro (Expo CLI). No state management library beyond the Apollo cache. No auth — identity is a name only (see §2 "Accounts"), and the deployment is reached over Tailscale, which is the real access boundary.

## 2. Backend API (GraphQL)

*   **Purpose:** Serves as the interface between the React frontend and the data storage/processing layers.
*   **Technology:** Apollo Server on Express (`expressMiddleware` mounted at `/graphql`, so plain routes under `/api` — `GET /api/activities/:id/download`, `/api/activities/:id/media/...`, `GET /api/export/full` — can sit alongside it; the `/api` prefix keeps them from clashing with web page paths), TypeScript on Node.js with ESM, no ORM.
*   **Accounts** (`backend/src/people.ts`): fully separate per-person data, identified by name only. `index.ts` builds the GraphQL context from the `X-GPX-Person` header (slugified; missing or invalid falls back to `DEFAULT_PERSON`, env, default `mark`). A person's files live in `GPX_FILES_DIRECTORY/<person>/`; top-level files belong to `DEFAULT_PERSON`. `fileIdentity()` turns a file path into its `gpx_filename` (path relative to `GPX_FILES_DIRECTORY`, so top-level files keep their bare basename) and `owner` (first folder segment). `listPeople()` (`people` query) is `DEFAULT_PERSON` plus every subfolder — there is no users table. Folder names that would collide with web routes (`stats`, `code`, …) are rejected.
    *   **Visibility:** every query that reads `activities` is filtered through `resolvers.ts`'s `visibleTo()` SQL fragment: the person's own activities plus ones shared with them in `activity_shares`. Shared activities count fully (lists, totals, PRs, streaks, heatmap — the heatmap cache is per person). `activity(id)` returns null for one the person can't see. The outlier/elevation-spike review lists are owner-only, since fixing edits the source file.
    *   **Ownership:** title/notes/type/trim/outlier-clean/elevation-fix/share require `owner = person`. `deleteActivity` from a share recipient only removes their share row.
*   **Key Operations:**
    *   **Queries:**
        *   Fetch individual activity details (`activity(id: ID!)`).
        *   Fetch aggregate statistics (`activitySummary`, `aggregatedStatsByType(activityType, startDate, endDate)`).
        *   Fetch paginated/filtered lists of activities (`activities(limit: Int = 20, offset: Int = 0, activityType: String, startDate: DateTime, endDate: DateTime)`). Returns data sorted reverse-chronologically by default.
    *   **Mutations:**
        *   Trigger re-analysis of data (`reanalyzeAllActivities`, `reanalyzeActivitiesByDateRange(startDate: DateTime!, endDate: DateTime!)`).
        *   Save a recorded track (`saveRecordedActivity(gpxContent: String!, clientId: String)`): validates the submitted GPX string minimally (size cap, looks like GPX), writes it to a server-generated filename in the requesting person's folder, `GPX_FILES_DIRECTORY/<person>/` — `recorded-<clientId>.gpx` when the app sends its recording UUID (validated as 8–64 letters/digits/dashes, written with an exclusive-create flag so a retried upload is a no-op), otherwise `recorded-<timestamp>-<random>.gpx` — and returns without waiting for ingestion — the file watcher (below) picks it up asynchronously through the normal pipeline.
        *   Permanently delete an activity (`deleteActivity(id: ID!)`): looks up `gpx_filename` from the DB row itself (never accepts a path from the client), `fs.unlink`s that exact file under `GPX_FILES_DIRECTORY` (tolerating an already-missing file), then deletes the `activities` row and its `activity_shares` rows — `activity_routes` cascades via its `activity_id` FK's `ON DELETE CASCADE`. Since the source file itself is removed, the watcher can't re-ingest it on a later restart/rescan. Owner only; for a share recipient it removes just their share.
        *   Share an activity (`setActivitySharedWith(id: ID!, people: [String!]!)`): the owner replaces the full set of people it's shared with ("did this with…"). Names must be in `listPeople()` and can't include the owner.
    *   **Full backup/export** (`GET /api/export/full`, plain Express route alongside `/api/activities/:id/download`): streams a `.zip` (via `archiver`) containing every raw source file under `GPX_FILES_DIRECTORY` (`gpx-files/`) plus an `activity-shares.json` (the one table that isn't derivable from the files) and a `db-export.json` with every `activities`/`activity_routes` row at full fidelity — `points_data`, `elevation_profile_data`, and `route_geom` (converted to GeoJSON via `ST_AsGeoJSON` so it round-trips as plain JSON rather than PostGIS binary). Reads only from the server's own `GPX_FILES_DIRECTORY` env var and DB connection, no client-supplied input. The DB rows are streamed into the archive one row at a time (an async generator piped through a `Readable`) rather than built as a single `JSON.stringify()`'d string — with ~500 activities' worth of `points_data`, a single pretty-printed string exceeds V8's per-string character limit (`RangeError: Invalid string length`) even though the raw data itself (~150MB across both tables) is well within the container's memory. For disaster recovery/migration to a new host; distinct from the Settings page's summary-only "Export Data" tab (`activities(limit: 10000)` GraphQL query), which excludes per-point track data.
*   **Resolver Logic:** `graphql/resolvers.js` queries `pg.Pool` directly with hand-written SQL (see `backend/src/graphql/resolvers.ts`). `activitySummary` and `aggregatedStatsByType` are computed live with `SUM`/`AVG`/`GROUP BY` on each request — there is no materialized view or cache.
*   **Immich media gallery integration** (`backend/src/immich/`, optional): `settings.ts` reads/writes the single-row `immich_settings` table (base URL + API key, the key never returned over GraphQL); `client.ts` wraps the subset of Immich's REST API needed — `/api/search/metadata` for scanning, `/api/assets/:id/(original|thumbnail)` for streaming; `match.ts` is the pure, unit-tested time-window + geo-tiebreak assignment logic; `scan.ts` orchestrates a scan (batches of 5 activities concurrently, same bounded-concurrency reasoning as `processor.ts`'s `processAll()`) and upserts results into `activity_media`. Two plain Express routes, `GET /activities/:id/media/:assetId` and `.../thumbnail`, proxy the actual asset bytes from Immich through the backend (same pattern as `/activities/:id/download`) so the API key and the Immich server itself never need to be reachable from the browser.

## 3. Database (PostgreSQL with PostGIS)

*   **Purpose:** Stores all processed activity data and route information.
*   **Technology:** PostgreSQL (`postgis/postgis:15-3.4` image), PostGIS extension for geospatial capabilities.
*   **Key Tables** (see `docs/DATA_MODEL.md` and `backend/db/init.sql` for the authoritative schema):
    *   `activities`: One row per GPX file (unique on `gpx_filename`) — owner, title, type, timestamps, distance, duration, speed, elevation stats.
    *   `activity_shares`: `(gpx_filename, person)` pairs for opt-in sharing. Keyed by filename so it survives re-analysis; not derived from the files, so wiping the volume loses it.
    *   `activity_routes`: One row per activity (`activity_id` PK/FK) — a PostGIS `GEOMETRY(LineString, 4326)`, plus a redundant `points_data` JSONB array (`{lat, lon, elevation, timestamp, hr, cad, atemp}` per point) and `elevation_profile_data` JSONB, since GeoJSON round-tripping loses elevation/timestamp per point. `hr`/`cad`/`atemp` (heart rate, cadence, ambient temperature) come from GPX's `<gpxtpx:TrackPointExtension>` and are `null` for the large majority of activities and always `null` for IGC/`.skiz`; `avg_hr`/`max_hr` on `activities` are derived from `hr` once at ingest.
*   There is no separate `activity_summary` or `aggregated_stats_by_type` table — those are computed on the fly by the resolvers, not pre-aggregated.
*   **Geospatial Capabilities:** `route_geom` has a GiST index; PostGIS functions aren't yet used for any query beyond storage (no geospatial queries — e.g. "activities near X" — are implemented).
*   **Migrations:** `init.sql` only runs on a fresh volume (via the Postgres image's init-script mechanism); there is no migration tool, so schema changes to an existing deployment need a manual `ALTER`/psql step. See [`TODO.md`](TODO.md).

## 4. Data Ingestion & Processing Pipeline

*   **Purpose:** Handles the parsing of raw GPX/IGC/Ski Tracks files and populates the PostgreSQL database.
*   **Trigger:** A `chokidar` file watcher (`backend/src/gpx/watcher.ts`) watches `GPX_FILES_DIRECTORY` recursively (per-person folders included, `_backups/` excluded) for `.gpx`, `.igc`, and `.skiz` files; on startup it fires an `add` event for every pre-existing file, then continues watching for new ones. Files land in that directory either externally (Syncthing/manual drop) or via the `saveRecordedActivity` mutation (Record page) writing a new file into the same directory — either way, the watcher is the single trigger into this pipeline.
*   **Components:**
    *   **GPX Parser** (`backend/src/gpx/parser.ts`): Uses the `gpxparser` npm package to read GPX files and extract track points/timestamps, then computes distance/speed/elevation stats gpxparser doesn't provide itself. Activity type is read from the GPX `<trk><type>` tag when present (mapped through a label table from raw values like `EMountainBikeRide`; a value that already matches a display label, as the phone app writes, is kept as-is), falling back to a filename-keyword guess (matches "running", "hiking", etc.), and left as "Unknown" if neither matches — no track-data heuristic runs at parse time (the phone app runs its own copy before upload and writes the chosen type); `ActivityDetail.jsx`'s chip picker (`track/suggestType.ts`'s band-fit heuristic, scored post-hoc against the activity's stored stats) offers the user a pick from a ranked list instead of the parser guessing on its own. `gpxparser` drops `<extensions>` entirely when building `track.points` (lat/lon/ele/time only), so heart rate/cadence/temperature (`<gpxtpx:TrackPointExtension>`'s `hr`/`cad`/`atemp`) are pulled back out separately by walking `gpx.xmlSource` — the full DOM `gpxparser` retains internally — with `querySelectorAll("trkpt")`/`getElementsByTagName("gpxtpx:hr")`, in the same document order `gpxparser` used to build `track.points`, so the two line up index-for-index without extra bookkeeping. The first track's `<desc>` fills `activities.notes` only while notes are empty, so a note edited on the web survives reprocessing.
    *   **IGC Parser** (`backend/src/igc/parser.ts`): For paragliding flight-recorder logs. Regex-parses `HFDTE` date headers and `B`-record fixes (lat/lon/altitude/timestamp) directly — no third-party IGC library — then computes distance/speed/elevation stats with a haversine helper (`haversineMeters`, exported for reuse), returning the same shape the GPX parser does. IGC has no track-name/type header, so title falls back to the filename stem and activity type is fixed to "Paragliding".
    *   **Ski Tracks Parser** (`backend/src/skiz/parser.ts`): For `.skiz` exports from the Ski Tracks app. The format is a zip archive containing `Track.xml` (a single `<track name="..." activity="...">` element, regex-extracted for title/activity type — no XML DOM lib, same approach as `gpx/writer.js`) and a headerless `Nodes.csv` (timestamp, lat, lon, elevation, course, speed, horizontal/vertical accuracy per line); unzipped via `adm-zip`. Reuses `igc/parser.js`'s `haversineMeters` for distance/speed/elevation stats rather than trusting `Track.xml`'s own precomputed metrics, for consistency with how GPX/IGC are handled. Verified against 91 real exports recovered from this deployment's Syncthing container (see `docs/SETUP.md`'s Ski Tracks note).
    *   **Database Writer** (`backend/src/gpx/processor.ts`): `processFile()` dispatches to whichever parser matches the file extension, derives `gpx_filename`/`owner` from the file's path (`people.ts`'s `fileIdentity()`), then upserts one activity + its route (keyed by `gpx_filename`, so re-processing the same file is idempotent) inside a single transaction. `parseActivityFile()` (the same per-extension dispatch, minus the DB write) is exported separately for the outlier-cleanup preview below, which needs to parse a scratch copy of a file without touching the database.
    *   **Reverse geocoding** (`backend/src/geocoding.ts`): `processFile()` resolves the activity's start point to a place name via Nominatim (`reverseGeocode()`) before opening a DB connection, storing the result in `activities.location_name`. Nominatim's usage policy caps requests at 1/sec, so `reverseGeocode()` self-throttles at the module level (≥1.1s between any two calls, regardless of caller) and always sends a descriptive `User-Agent`. This still isn't safe to run unthrottled across many files at once, so it's skipped (`{ skipGeocode: true }`) both by `processAll()`'s concurrent batches and by the watcher's startup replay of pre-existing files (gated on chokidar's `ready` event, so a backend restart doesn't re-request geocoding for the whole library) — only a genuinely new file passing through the watcher after startup triggers a live lookup. It's also skipped when the activity already has a `location_name` (the upsert preserves the existing value via `COALESCE` on a skipped lookup). Backfilling existing rows uses a separate, explicitly-throttled one-off script (`backend/scripts/backfillLocationNames.js`), not this ingest path. A lookup failure (network error, timeout, non-2xx) is caught and leaves `location_name` `NULL` rather than failing ingestion.
    *   **GPS outlier detection (manual, opt-in)** (`backend/src/track/outliers.ts`, `geo.js`): stats/`points_data` are always computed from the *raw*, unfiltered points — no automatic filtering happens at ingest. `detectOutliers()` flags points implying a >55 m/s (~200 km/h) jump from the last non-flagged point, for the user to review on the Settings page (`activitiesWithOutliers` query) and Activity Detail page (`activityOutlierDiff` query, `cleanActivityOutliers` mutation) before deciding to remove them. A duplicate/out-of-order timestamp (dt ≤ 0) is never flagged regardless of distance — speed can't be evaluated for it, same as a missing timestamp. When a jump does exceed the threshold, the point right after it is checked for corroboration (does it continue on plausibly from the jump, rather than snapping back toward the pre-jump trajectory?) before flagging: some devices freeze position for several samples during a stop and need one sample to "catch up" once movement resumes, producing a real (if mistimed) jump that a naive last-kept-point comparison can't tell apart from a genuine bad GPS fix, and would otherwise keep cascade-flagging the real points that follow it since they're all still far from the stale anchor. A corroborated jump is trusted and becomes the new anchor instead of being flagged. `activityOutlierDiff`'s before/after stats come from actually running the removal against a throwaway copy of the source file and re-parsing it with the real per-format parser (via `parseActivityFile()`), not from a generic haversine estimate over `points_data` — `gpx/parser.js` trusts `gpxparser`'s own (non-haversine) distance/elevation algorithm for `.gpx` files, so an estimate would silently disagree with what cleaning actually produces once saved. `cleanActivityOutliers` supports `.gpx`, `.skiz`, and `.igc` (new `igc/writer.js`, added alongside `gpx/writer.js`/`skiz/writer.js`'s existing `removeGpxTrackPoints`/`removeSkizTrackPoints`) — wider format support than title/type/trim editing, which stays `.gpx`/`.skiz`-only.
    *   **Lift (chairlift/gondola) detection** (`backend/src/track/liftDetection.ts`, reusing `geo.js`'s `bearingDegrees`/`bearingDiffDegrees`): a track-shape heuristic run against any activity's `points_data`, not gated by `activityType` — a lift ride can appear inside a hike or ski day alike. `detectLiftSegments()` flags contiguous stretches that are straight-line (heading drift under 20°), roughly constant speed (moving-interval coefficient of variation under 0.4, allowing stops up to 3 minutes), spend at least half the segment's duration actually moving (catches a mostly-stationary stop with drifting GPS/elevation, which can otherwise pass every other check since no single stall exceeds the 3-minute cap), and climb steadily uphill (at least 20 m net gain, 70%+ of elevation steps matching the net direction) — distinct from a hiker's or skinner's noisier stop-start pace. Uphill-only: a straight, steady, fast descent (e.g. a bike-park trail) can otherwise pass the same checks and get mistaken for a lift ride down, and every consumer of this data only ever used positive gain anyway. Detection-only, computed live on every `Activity.route` fetch (`liftSegments` field, rendered as purple bands on the Activity Detail elevation chart) and surfaced in aggregate via the `activitiesWithLiftSegments` query (Settings page's "Suspected Lift Rides" list) — nothing is stored or mutated. The frontend derives a "gain excluding lift" stat by subtracting each segment's positive elevation gain from `totalElevationGain`, rather than the backend persisting a separate column.
    *   **Elevation spike detection (manual, opt-in)** (`backend/src/track/elevationSpikes.ts`): a different failure mode than GPS outlier detection above — a single point (or short run) whose *elevation* jumps sharply off trend and back, a bad altitude reading rather than a GPS teleport or real terrain, which the horizontal-speed-based outlier detector and the ingest-time elevation smoothing both miss. `detectElevationSpikes()` works off single-step elevation deltas: finds a sudden "entry" jump, then the nearest later "exit" jump of roughly the same size landing back near the pre-entry elevation, and flags everything between — this scales correctly regardless of how long the glitch plateau lasts (unlike a local-window/median approach, which loses the middle of a long plateau once the window fills with other spiked points) and never flags a real sustained climb/descent, since that never reverses back toward where it started. `correctElevationSpikes()` returns a corrected copy with each flagged run linearly interpolated between its nearest good neighbors. Surfaced via `activitiesWithElevationSpikes` (Settings page's "Elevation Spikes" list) and `activityElevationFixDiff`/`fixActivityElevationSpikes` (Activity Detail's "Elevation Spikes" preview-and-normalize tool) — same opt-in, review-before-saving model as GPS outlier cleanup. Unlike outlier cleanup, fixing rewrites just the elevation field of flagged points in place (new `fixGpxElevations`/`fixIgcElevations`/`fixSkizElevations` in the three `writer.js` files) rather than removing points, since the position fix was fine and only the altitude reading was bad.
*   **Re-analysis:** The `reanalyze*` mutations call `reanalyzeAll()` / `reanalyzeByDateRange()` in `processor.js`, which re-run this same pipeline over existing files (`reanalyzeAll` walks subfolders, skipping `_backups/`). Re-analysis is global, not per person.
*   **Concurrency:** Both the watcher (strict FIFO, one file at a time) and `reanalyze*` (batches of 5 via `processAll()`) bound how many files are processed concurrently, since the default `pg.Pool` only has 10 connections — see `.agents/docs/ingestion.md` and `docs/SETUP.md` §5 for the pool-exhaustion incident this guards against.

## Integration Flow

1.  The phone app uploads a recorded activity (`saveRecordedActivity`), which the backend writes into the monitored directory — or the user drops GPX, IGC, or Ski Tracks (`.skiz`) files there manually.
2.  The **file watcher** detects new files, the **parser** extracts metrics, and the **processor** upserts activity + route data into **PostgreSQL**.
3.  The **Expo web UI** (and the phone app's History) makes GraphQL queries to the **Backend API**.
4.  The **Backend API** (GraphQL resolvers) queries the **PostgreSQL Database** for activity details, aggregate stats, or route geometries.
5.  For re-analysis, the **web UI** (Settings page) triggers a GraphQL mutation, which instructs the **Backend API** to re-run the ingestion pipeline over existing files, optionally scoped to a date range.
6.  Map and elevation data are rendered in the **web UI** using `react-leaflet` and `recharts`.
